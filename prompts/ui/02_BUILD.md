# 화면 구현 프롬프트
사용 시점: 설계 범위를 정한 뒤 구현하거나, 기존 화면을 수정할 때.
전체 문서를 매번 읽지 말고 현재 작업과 연결된 항목만 확인한다.

## 요청
runtime/REQUIREMENTS.md와 runtime/DESIGN.md의 관련 요구·결정을 근거로 화면을 구현해줘. 나는 제출 후 실제 코드의 구조와 동작을 설명해야 한다.

1. 기존 프로젝트의 기술 스택·컴포넌트·계약을 우선 활용한다. 새 라이브러리는 필요한 이유가 있을 때만 추가한다.
2. 핵심 사용자 흐름 하나를 입력부터 결과 표시까지 먼저 연결한다. 꾸미기는 필수 동작을 확보한 후 진행한다.
3. 화면 표시, 입력 처리, 핵심 계산·판정의 역할을 명확히 구분하되 파일 수를 늘리기 위한 분리는 하지 않는다.
4. 함수·변수에 업무 의미가 드러나는 이름을 붙인다. 중복 상태와 불필요한 추상화를 피한다. 중요한 규칙의 주석에는 이유와 근거를 남긴다.
5. 해당하는 로딩·빈 데이터·오류·확인 필요 상태를 구현한다. 색상만으로 상태를 구분하지 않는다. 읽기 쉬운 표·레이블·포커스와 필요한 화면 폭을 고려한다.
6. 실제 처리 결과와 화면 값이 연결되어야 한다. 미구현 동작을 성공 메시지나 가짜 데이터로 숨기지 않는다.
7. 정상 경로와 중요한 실패 경로를 검증한다. 기대값은 요구사항에서 정한다. UI 자동 조작·캡처는 하지 않는다. 화면 검증은 사용자 수동 확인 절차를 제공한다.
8. 설계와 구현이 달라졌다면 DESIGN에 이유를, 검증은 VERIFICATION에, 작업·오류는 WORKLOG에 기록한다.

## 핵심 흐름 완성 시 보고
- 변경한 파일과 충족한 요구
- 대표 입력 한 건: 입력 → 처리 함수 → 결과 → 화면 표시 (실제 파일·함수명)
- 실행한 검증과 미검증 항목
- 한계와 다음 우선순위

작은 UI 수정마다 이해 확인 질문으로 멈추지 않는다. 핵심 흐름 완료 시 03_REVIEW.md로 점검한다. 별도 요청 없이 전체 화면을 재설계하지 않는다.
