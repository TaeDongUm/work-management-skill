# 공통 검토·설명 프롬프트
핵심 기능이 완성되거나 중요한 수정 후 사용한다. UI가 없는 데이터·CLI·서버 과제에도 적용한다.
제출 후 AI 금지 서술형 단계에서는 사용하지 않는다.

## 요청
관련 요구·원자료·실제 코드·검증 결과를 대조해줘. 작성자의 기존 설명을 정답으로 가정하지 마.
1. 대표 입력 한 건을 실제 파일·함수 기준으로 따라가며 입력 → 검사 → 처리 → 저장·출력 경로를 설명한다.
2. 필수 요구 누락, 경계값·중복·누락·실패 처리, 민감정보·데이터 손실 위험 중 관련된 것을 찾는다.
3. 기대값을 원자료에서 정해 검증한다. 코드가 만든 결과를 그대로 기대값으로 복사하지 않는다.
4. 발견 사항마다 위치·재현 조건·영향·최소 수정·재검증 방법을 제시한다. 미실행이면 명시한다.
5. 중요한 결정의 이유·대안·한계와 실제 구현의 불일치를 찾는다.
6. 실행 결과는 VERIFICATION, 설계 수정은 DESIGN, 오류·작업은 WORKLOG, 사용자 이해 확인은 UNDERSTANDING에 기록한다.

## 사용자 이해 확인
동작·구조·선택 이유·실패 조건 중 중요한 질문 하나를 실제 코드 기준으로 한다.
사용자 답변 전에 모범 답안을 제공하지 않는다. 답변을 받으면 코드와 실행 근거에 비추어 교정한다.
필요하면 질문 → 코드 확인 → 실행 확인 → 자기 말로 설명을 진행한다.
AI의 설명은 사용자 이해의 증거가 아니다. 사용자가 답하지 않으면 미확인으로 둔다.
작은 수정마다 반복하지 않는다. 시간 부족 시 중요한 규칙과 실패 조건부터 점검한다.

## 별도 검토 세션 — 선택
허용된 내부 환경에서 중요한 합의·제출 전 코드 검토에 한정해 고려한다. 상시 감시 세션이나 다중 에이전트 실행을 자동으로 시작하지 않는다.
사용자가 별도 검토를 선택하면 원문 요구, 실제 코드 위치, 실행 방법과 검증 결과를 제공하고 동일한 결론을 유도하지 않는다.
추가 AI의 지적도 가설이다. 실제 증거·재현으로 확인한 뒤 수정한다.

## 단계별 이해 확인과 검증 책임
초기 과제·데이터, 중요한 설계 선택, 핵심 구현·큰 변경에서도 이해 확인을 수행한다.
사용자의 목표 이해를 원문과 대조하고, 실제 파일·함수·테스트와 설명을 연결한다.
검증은 기준 확정 여부, 실제 실행 결과, 사용자 이해 상태를 따로 본다.
AI가 작성/실행한 검사와 사용자가 직접 실행/로그 확인/화면 확인한 일을 정확히 구분한다.
주요 질문: 왜 선택했나·대안·포기한 것 / 실제 호출 경로 / 값 변경 영향 / 오류 원인·AI 제안·선택 / 검증 근거·남은 범위.
답변은 UNDERSTANDING의 U ID, 관련 실행 증거는 VERIFICATION에 기록한다.
