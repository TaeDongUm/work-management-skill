# 평가 관점 점검 → 보완 작업 프롬프트
사용 시점: 핵심 흐름을 처음 완성한 후, 제출 여유를 남긴 최종 점검 시.
매 커밋마다 전체 평가를 반복하지 않는다. 수정 후에는 영향 항목만 다시 확인한다.

## 요청
prep/EVALUATION_REFERENCE.md의 참고 기준으로 실제 과제의 현재 상태를 점검해줘.
이는 후기 기반 자체 점검이며 공식 점수 예측이 아니다.
현재 남은 시간, 과제의 필수 요구, 실제 코드·원자료·실행 결과·사용자 설명을 근거로 판단한다.

1. 관련 파일과 증거를 확인한다. 문서의 '완료' 표기를 그대로 믿지 않는다.
2. 각 참고 항목을 충족 / 부분 충족 / 미충족 / 미확인 / 해당 없음으로 판정하고 이유와 증거 위치를 남긴다.
3. 구현 결함, 검증 부족, 기록 불일치, 사용자 이해 미확인을 구분한다.
4. 인지 항목은 실제 사용자의 설명으로만 판단한다. 필요한 질문은 01_REVIEW_AND_EXPLAIN.md 방식으로 한다.
5. 결함과 위험을 묶어 같은 문제를 여러 항목의 중복 작업으로 추가하지 않는다.
6. 보완 작업을 runtime/WORKLOG.md의 작업표에 추가하거나 기존 작업과 병합한다.
   각 작업에 관련 R ID, 평가 항목, 완료 기준, V ID 또는 U ID, 예상 소요, 우선순위를 연결한다.
7. P0: 필수 기능·정확성·데이터 안전·제출을 막는 문제.
   P1: 중요한 실패 경로·검증 공백·핵심 이해 부족.
   P2: 장식·부가 기능·낮은 영향 정리. 시간 부족 시 보류한다.
   실제 영향에 따라 우선순위를 조정하고 예상 소요는 추정으로 표시한다.
8. 즉시 실행할 작업은 우선순위 상위 최대 3개부터 선택한다. 제출 여유를 남기고 큰 재설계는 피한다.
9. 이미 승인된 범위의 안전한 수정·검증은 계속 수행한다. 담당자 확인·사용자 답변이 필요한 부분만 대기한다.
10. 수정 후 해당 검증을 다시 실행하고 실제 근거가 생겼을 때만 판정을 갱신한다.

## 금지
점수용 가짜 합의·커밋·테스트·이해 기록, 불필요한 기능 추가, 문서 개수 늘리기, 범용화 자체를 목표로 한 재설계를 하지 않는다.
공식 안내와 충돌하면 공식 안내가 우선이다. 확인할 수 없는 항목은 미확인으로 남긴다.

## 출력과 기록
WORKLOG의 평가 관점 점검 표에 최신 점검 상태를 기록한다. 중요한 이전 실패·수정 근거는 기존 오류·검증 이력으로 보존한다.
답변에는 가장 큰 결함, 지금 할 작업, 보류할 작업과 이유, 다음 재검증만 짧게 제시한다.
