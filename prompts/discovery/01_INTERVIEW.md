# 질문·재질문·역제안
초기 원문·데이터 조사를 마친 뒤 사용한다. 코딩 AI가 질문 문안을 만들고 실제 담당자 답변은 사용자/허용된 채널에서 받는다. 답을 지어내지 않는다.

## 질문 선정
자료에 없는 조건 중 결과·설계·판정을 바꾸는 것 최대 3개를 우선한다.
최근 실제 사례 → 현재 처리 → 병목·영향 → 사용자·판단자 → 예외·경계 순으로 필요한 것만 묻는다.
질문마다 답이 달라지면 무엇을 다르게 구현할지 적는다. 원문 위치와 데이터 근거를 먼저 확인한다.

## 모호한 답변을 받았을 때
1. 업무 정책인지, 사실·데이터 부족인지, 개발자가 결정할 구현 방법인지 구분한다.
2. 중요한 쟁점은 구체적 사례·양자 비교·허용 불가능한 결과로 1~2회 짧게 재질문한다. 횟수는 절대 제한이 아니라 시간 관리 기준이다.
3. 여전히 미정이면 기본안과 대안, 이점·포기하는 것·실패 조건을 설명하고 역제안한다.
4. '알아서 하세요'가 기술 선택 위임이면 스스로 결정하고 DESIGN에 이유를 기록한다. 업무 조건까지 모두 확정된 것으로 간주하지 않는다.
5. 중요한 미해결 정책은 임시 가정/차단으로 표시한다. 원문 필수 조건·안전·데이터 손실과 충돌하는 결정을 임의로 하지 않는다.
6. '있으면 좋다'는 필수/선택 우선순위를 확인한다. 침묵은 합의가 아니다. 원문과 답변이 충돌하면 명시한다.
7. 옵션화는 담당자가 실제 조정할 값에만 쓴다. 기본값·단위·허용 범위·결과 영향·불가능할 때 처리를 정한다.
8. REQUIREMENTS의 해당 R/질문 항목을 갱신하고 변경 영향은 prompts/change/PROPAGATE_CHANGE.md로 전달한다.

## 역제안 문장
“현재 확인된 조건은 [조건]이고 [정책]은 미정입니다.
이번에는 [기본안]으로 구현하면 [이점]을 얻지만 [대가/한계]가 있습니다.
대안은 [대안]입니다. [구체적인 업무상 결과]를 허용하는 방향으로 진행해도 될까요?”

버스 예시는 질문 방식만 연습한다. 실제 과제 요구로 복사하지 않는다:
- '버스가 너무 많으면 안 된다' → '모든 이용자 탑승과 차량 수 감소가 충돌하면 어느 쪽을 우선하나요?'
- '도보가 길면 곤란하다' → '예외를 허용하지 않는 상한인가요, 초과 인원을 줄이는 목표인가요?'
- '군집화를 어떻게 할까요?'는 개발자 설계 질문이다. 담당자에게는 접근 거리·탑승 대상·우선순위 등 업무 기준을 묻는다.

## 짧은 합의
문제 / 근거 / 만들 것·제외 / 완료 조건 / 남은 미확정을 짧게 확인한다.
이미 명확한 요구·일상적인 기술 선택까지 승인을 반복하지 않는다. 수치·성과·합의를 만들어 채우지 않는다.
