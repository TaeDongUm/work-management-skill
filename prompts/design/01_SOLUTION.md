# 계산·구조·검증 설계
사용 시점: 초기 과제·데이터 확인 후. UI 설계보다 먼저 핵심 처리 문제를 정의한다.

## 요청
관련 요구·데이터·기존 코드에 근거해 핵심 해결 방식을 설계해줘.

1. 입력 / 결정할 값 / 필수 제약 / 개선 목표·우선순위 / 출력 / 실패 처리를 분리한다.
2. 복합 문제는 하위 문제와 입출력 연결을 정리한다. 한 알고리즘이 전체를 해결한다고 가정하지 않는다.
3. 설명 가능한 기본 방식과 현실적인 대안 1~2개를 비교한다.
   정확성·필수 조건·실행시간·구현 비용·이해 가능성·데이터 제약을 기준으로 선택하고 포기하는 것을 적는다.
   조건을 만족하는 해와 최적해를 구분하고, 최적성을 증명하지 않았다면 보장한다고 쓰지 않는다.
4. 알고리즘이 필요한 과제는 작은 수작업 예제·독립적인 제약 검사·기준 방식과의 비교를 먼저 정한다.
   휴리스틱/솔버/군집화는 필요한 경우에만 검토한다. 후보 축소·이상치 제외로 대상이나 유효한 해가 빠지는지 확인한다.
5. 기술 스택은 기존 환경을 우선한다. 각 새 선택의 역할·현장 근거·대안·한계를 DESIGN에 적는다.
   Python·SQLite 등을 관성적으로 선택하지 않는다. 동시성·설치·실행 조건을 고려하되 불필요한 확장은 하지 않는다.
6. 입력 처리·계산·저장·표시의 책임과 인터페이스를 정한다. 파일 수를 늘리기 위한 분리는 하지 않는다.
   계산을 HTTP·DB와 독립적으로 실행할 수 있는지 확인한다. 요구된 인증·권한·Docker는 장식으로 취급하지 않는다.
7. 작업을 핵심 3~4개 묶음으로 정리하고 첫 작은 흐름을 입력부터 결과까지 연결한다.
   미확정 조건이 영향을 미치는 부분은 분리하고 무관한 작업은 진행한다.
8. DESIGN·VERIFICATION·WORKLOG의 해당 항목만 갱신한다.
   중요한 선택 하나에 대해 대안·대가를 내 말로 설명하게 하고 UNDERSTANDING에 연결한다.

## 반례 찾기 — 전부 구현할 목록이 아님
누락·중복 / 자원 부족 / 한도 바로 전·같음·직후 / 수요 집중 / 조건끼리 충돌 /
해가 없음 / 설정 변경 / 저장 실패·권한 위반 중 관련 있는 위험만 찾는다.
필수 조건 위반·데이터 손실·핵심 결과 오류를 우선하고, 낮은 영향은 이유와 함께 보류한다.
값 변경의 예상 영향과 실제 실행 결과를 구분한다. 휴리스틱의 결과가 항상 단조롭게 좋아진다고 주장하지 않는다.
