# 후기와 평가 설명 검토
준비 전략의 근거를 구분하는 참고 문서. 시험 중 전체를 AI 문맥에 넣지 않는다.

## 출처
- 공식 Cofa 소개: https://www.getcofa.com/ko
- Luka 후기: https://brunch.co.kr/@luma/5
- 후기 본문과 2026-10-29 댓글은 사용자가 대화에 제공한 내용 기준.
- 현재 시험 규정은 사용자 제공 공식 PDF를 기준으로 한다. 과거 대회 조건을 현재 시험에 적용하지 않는다.

## 확인 수준
| 내용 | 분류 | 채택할 행동 |
|---|---|---|
| 기술·의도·인지, 산출물·작업 기록·사후 Q&A 확인 | 공식 일반 설명 | 구현·검증·설명을 연결 |
| FDE 소통 축과 handoff 고평가 사례 | 작성자 관찰 | 필요한 인계가 가능하도록 기록 |
| 의도 축의 변별력이 컸고 인지가 낮았다는 평가 | 당시 관찰·해석 | 이번 시험 배점으로 단정하지 않음 |
| 모르는 것을 AI에 묻는 것이 가점에 가깝다 | 작성자 의견 | 질문 후 코드·실행·내 설명 확인 |
| 정해진 틀을 따라야 고득점한다 | 작성자 해석 | 형식보다 실제 판단·검증의 질에 집중 |
| 범용 제품으로 도메인 문제 80% 해결 | 준비했으면 좋았겠다는 가설 | 검증된 재사용률·반입 허용 근거로 쓰지 않음 |

## 작성자가 실제 준비한 것
FDE·환경 조사, 하네스 제작, 도구 선택·보안 설정, 가상 담당자 리허설, 발견된 결함 반영.
작업 중 인터뷰·합의·판단 원칙·진행 단계·교차검증을 사용했다고 설명한다.
예상과 달리 README가 상세해 문제 발굴에 대한 준비가 그대로 맞지는 않았다고 회고한다.

## 우리가 채택할 것
- README를 먼저 읽고 남아 있는 중요한 불확실성을 질문한다.
- 범위·완료 기준을 확인하고 작은 핵심 흐름부터 구현한다.
- 계산·명확한 규칙은 코드로 처리하고 실제 결과를 검증한다.
- 필요할 때 handoff를 작성한다.
- 코드 선택 이유와 실제 한계를 작업 중 이해한다.

## 그대로 따르지 않을 것
- 질문 수, 문서 수, 커밋 수를 평가 목표로 삼기.
- 모든 과제에 많은 분석 관점과 복잡한 하네스를 강제하기.
- 고정된 시간마다 세션을 끊거나 감시용 세션을 반드시 운영하기.
- 공개했다는 이유만으로 완성 앱 반입이 허용된다고 가정하기.
- 과거 225분·5문항·3분 조건을 현재 시험에 적용하기.

## 추가 의견을 AI에게 묻는 양식
> 아래 주장을 공식 확인·작성자 경험·해석·미확인으로 구분해줘. 실제 과제 해결에 도움이 되는 행동과 형식만 늘리는 행동을 나눠줘. 현재 시험 규정과 충돌하는 부분은 따로 표시하고, 우리 WORKFLOW를 바꿀 필요가 있는 근거만 제시해줘.
