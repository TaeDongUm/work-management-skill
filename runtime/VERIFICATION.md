# 검증 계획과 실행 결과
상태: 과제 시작 전. 계획과 실행을 구분한다.

## 작성 규칙
- 기준: 무엇이 맞아야 하는가.
- 방법: 어떤 입력·행동으로 확인하는가.
- 시점: 구현 직후·연결 후·관련 변경 후·제출 전 중 언제 필요한가.
- 기대 결과는 REQUIREMENTS의 규칙과 원자료에서 정한다.
- 영향이 큰 실패를 우선한다. 테스트 수나 커버리지 수치 자체를 목표로 삼지 않는다.
- 모의 의존성 테스트는 실제 연결 검증과 구분한다.

## 검증 계획
| V ID | R ID | 입력·사전조건 | 기대 결과·근거 | 방법·테스트 위치 | 실행 시점 | 중요도 |
|---|---|---|---|---|---|---|

방법 예: 계산 단위 테스트 / API·DB 통합 테스트 / 원본 대조 / 생성 파일 재조회 / 사용자 수동 화면 확인.

## 실행 이력
| 실행 ID | V ID | 대상 버전·변경 상태 | 실행 주체 | 명령·수동 절차 | 실제 결과·근거 | 상태 |
|---|---|---|---|---|---|---|

상태: 통과 / 실패 / 미실행 / 차단됨.
대상 버전은 실제 커밋 또는 파일·변경 상태로 식별한다. 없는 커밋·시간·로그를 만들지 않는다.
실행 주체는 AI 도구 실행 / 사용자 직접 확인 등을 구분한다.
화면 검사는 실제 사용자가 확인한 결과를 받아 기록한다. 화면 캡처나 자동 조작을 요구하지 않는다.

## 변경 이후 재검증 필요
| 변경 내용 | 영향받는 V ID | 이전 결과를 그대로 쓸 수 없는 이유 | 현재 상태 |
|---|---|---|---|

## 제출 전 확인
- [ ] 필수 요구마다 유효한 검증 결과 또는 미검증 이유가 있다.
- [ ] 최종 변경 후 필요한 재검증을 했다.
- [ ] 생성 파일을 실제로 다시 읽어 형식·내용을 확인했다.
- [ ] 실패·차단·모의 검증을 통과로 바꾸어 기록하지 않았다.
- [ ] 실제 실행법과 제출 파일이 일치한다.

체크는 실제 확인 후에만 한다. 관련 없는 항목은 이유와 함께 해당 없음으로 표시한다.
