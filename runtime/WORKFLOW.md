# 과제 수행 지침
제공 README·기존 AGENTS.md·시험 규정이 우선이다. 이 문서는 프레임워크나 코드 구조를 강제하지 않는다.

## 시작
1. 기존 요구사항·자료·코드·실행법·테스트를 조사한다.
2. REQUIREMENTS.md에 필수 요구·근거·제약·미확인을 구분한다.
3. 자료에 없는 사항 중 답에 따라 설계·판정·우선순위가 달라지는 질문을 선별한다.
4. 담당자 답변을 얻지 못한 사항은 가정 또는 미확인으로 남긴다.
5. 중요한 결정과 기대 결과를 정한 후 작은 핵심 흐름을 구현한다.

## 작업 지시 틀
목표 / 관련 요구 ID / 범위 / 유지할 제약 / 완료 기준·검증 ID / 막힐 때 판단 기준.
일상적인 수정은 승인 요청을 반복하지 말고 진행한다. 요구 충돌·중요한 범위 변경·허용 여부 불명확은 사용자에게 알린다.

## 구현과 검증
- UI가 필요한 과제는 ../prompts/ui/01_PLAN.md → 02_BUILD.md → 03_REVIEW.md를 해당 단계에만 참고한다. 전체를 매번 읽지 않는다. UI가 없으면 생략한다.
- Codex 단독 설계·구현을 기본으로 한다. UI UX Pro Max 같은 추가 도구는 구체적 필요가 있을 때만 검토한다.
- 제공 프로젝트가 있으면 기존 구조·계약을 우선 유지한다.
- 규칙·계산과 화면을 필요에 맞게 분리한다. 과설계하지 않는다.
- 핵심 흐름을 끝까지 연결하고 중요한 실패 경로를 확인한다.
- 기대값은 요구사항에서 도출한다. 구현 결과를 그대로 정답으로 쓰지 않는다.
- 실제 실행 없이 테스트 통과·저장 완료·화면 정상이라고 보고하지 않는다.
- 실패하면 원인과 수정 범위를 좁히고 같은 조건으로 재검증한다.
- 코드 변경 후 관련 검증 결과가 여전히 유효한지 확인한다.
- UI 자동 조작은 사용하지 않는다. 화면은 사용자가 허용된 내부 브라우저에서 확인한다.
- 외부 API·전송·개인 인증을 임의로 추가하지 않는다.

## 기록
- 새 요구·합의: REQUIREMENTS.
- 중요한 설계·화면 선택: DESIGN.
- 검증 계획·실행 결과: VERIFICATION.
- 작업·우선순위 변경·오류·이해 확인: WORKLOG.
- 세션 전환 시 현재 상태: HANDOFF.
- 매 대화·명령마다 기록하지 않는다. 중요한 변경 또는 작업 단위 종료 때 갱신한다.
- 동일 사실을 복제하지 말고 ID와 파일 위치를 참조한다.
- 사용자 직접 확인·설명은 사용자가 실제 제공한 경우에만 기록한다.
- 이해 확인은 핵심 흐름 완성 시에만 수행한다. 작은 수정마다 질문을 위해 멈추지 않는다.

## 시간 관리
초기 조사 후 핵심 흐름 구현을 우선한다. 시간이 부족하면 부가 기능을 보류하고 필수 동작·검증·제출 여유를 확보한다.
180분 연습 배분 참고: 조사 20 / 범위·설계 15 / 핵심 구현 60 / 필수 확장 40 / 검증·수정 25 / 최종 확인·제출 20분.
실제 요구와 필수 시작 절차·남은 시간에 맞춰 조정한다.

## 작업 종료 보고
- 완료한 요구·변경 파일
- 실제 실행한 검증과 결과
- 미검증·실패·남은 한계
- 다음으로 할 가장 중요한 일
장황한 자기평가나 점수 예측은 하지 않는다.

## 제출 전
제출 형식·파일 위치·실행 명령을 확인한다. 최종 코드로 핵심 검증을 수행하고 생성 파일을 다시 읽는다.
문서가 실제 동작과 일치하는지, 알려진 한계가 숨겨지지 않았는지 확인한다.
최종 제출 완료는 플랫폼의 제출 결과로 확인한다.


## 발굴·합의와 규칙 구현
- 시작 시 ../prompts/discovery/01_INTERVIEW.md를 필요한 범위만 사용한다. 이미 명확한 요구는 반복해서 묻지 않는다.
- 중요한 업무 규칙·범위·완료 기준은 REQUIREMENTS의 합의 요약으로 확인한다. 가정을 합의로 바꾸어 적지 않는다.
- 확정된 계산·판정 규칙은 재현 가능한 코드로 구현한다. 불명확한 규칙은 임의 확정하지 않는다.
- 원자료 → 확인된 규칙 → 코드 → 독립적으로 정한 기대값을 연결한다. 코드로 만들었다는 사실만으로 정확성을 보장하지 않는다.

## 단계 전환 점검
범위 확정 후 / 첫 핵심 흐름 완성 후 / 제출 전에 다음을 확인한다. 매 커밋마다 의무 기록하지 않는다.
1. 방향: 구현이 확정 요구와 연결되는가?
2. 증거: 완료 표시마다 실제 실행 근거가 있는가?
3. 반례: 정상 외 누락·중복·실패 등 중요한 예외를 확인했는가?

## 평가 관점에서 보완하기
첫 핵심 흐름 완성 후 ../prompts/review/02_GAP_REVIEW.md로 점검한다.
후기 기반 참고표이며 공식 점수는 예측하지 않는다. 부족한 점은 WORKLOG 작업으로 병합·추가하고 우선순위 상위 최대 3개부터 수행한다.
수정 후 관련 항목만 재검증한다. 제출 여유를 남기고 점수용 과설계·가짜 기록을 하지 않는다.
전체 과제의 구조·규칙·실패 조건 이해는 ../prompts/review/01_REVIEW_AND_EXPLAIN.md로 확인한다. UI 검토와 같은 질문을 중복 수행하지 않는다.
